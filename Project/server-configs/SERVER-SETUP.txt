Eine `Frontend/JS/SDK.js` oder SDK-Vorlage existiert nicht mehr. `dataClient.js`
bildet bei HTTPS aus der aktuellen Browser-Origin automatisch
`wss://<gleicher-host[:port]>/ws`.

HTTP-Routen:

  GET /version                 Paketversion
  GET /live                    Prozess lebt; beim Shutdown 503
  GET /ready, GET /health      initialisierte und aktuelle Abhaengigkeiten
  GET /status                  Detailstatus, nur mit Admin-Session
  GET/POST/DELETE /api/session Sessionstatus, Login und Logout
  POST /api/password           Eigenes Passwort
  POST /api/password-reset     Reset mit einmaligem Nachweis
  POST /api/password-setup     Erstvergabe nach KennwortVergessen-Freigabe
  POST /api/admin/password-reset Admin erzeugt Reset-Nachweis
  POST /api/admin/password-setup Admin setzt/entfernt Erstvergabe-Freigabe
  POST /api/admin/password     Admin setzt Passwort direkt
  GET/POST/DELETE /api/monitor/session Monitor-Session
  GET /ws                      WebSocket-v2-Upgrade und RPC/Subscriptions

Die WebSocket-RPCs decken oeffentliche Daten/Scoreboards, authentifizierte
Profile/Forderungen/EntryList, Operator-Court-/Navigatorsteuerung,
Admin-Monitorverwaltung und Geraete-ACKs ab. Cookies, Rollen und Origins werden
serverseitig geprueft; localStorage ist keine Rollen- oder Sessionautoritaet.
Die verbindliche Bedeutung terminaler und temporaerer WebSocket-Schliesscodes
steht in `Project/software/WEBSOCKET-CLOSE-CODES.txt`.

Die oeffentliche Passwort-Erstvergabe verlangt eine aktive Person und den Wert
`x` in `Personen.KennwortVergessen`. Der Admin schaltet diese Freigabe mit
`allowed: true|false`; ein erfolgreicher Setup-Write setzt das Passwort, leert
die Freigabe atomar und widerruft alle Sitzungen der Zielperson vor und nach dem
Write. Aktivstatus und Freigabe werden unmittelbar vor dem Write erneut geprueft.

2. SYSTEME, TLS UND PORTS
================================================================================

System | Verzeichnis              | Externe Origin              | Backend
-------|--------------------------|------------------------------|----------------
Live   | /srv/http/ePiber/piber   | https://epiber.at            | 127.0.0.1:8080
PAJ    | /srv/http/ePiber/paj     | https://epiber.at:8081       | 127.0.0.1:8083
PK     | /srv/http/ePiber/pk      | https://epiber.at:8082       | 127.0.0.1:8084

WebSockets verwenden entsprechend `wss://epiber.at/ws`,
`wss://epiber.at:8081/ws` und `wss://epiber.at:8082/ws`. HTTP oder `ws://` ist
fuer keines der drei Systeme ein freigegebener Browsertransport.

Caddy terminiert TLS fuer alle Origins, ausdruecklich auch auf den Ports 8081 und
8082. Nur Caddy ist extern erreichbar. Die Firewall gibt TCP 80 und 443 fuer
Zertifikat und den HTTP-zu-HTTPS-Weg der Live-Origin sowie TCP 8081 und 8082 fuer
die HTTPS-Testsysteme frei. TCP 8080, 8083 und 8084 bleibt gesperrt. DNS
`epiber.at` zeigt auf den Server. Zertifikate validieren den Hostnamen
`epiber.at`, nicht einen Port; dasselbe passende Hostzertifikat muss daher an
allen drei TLS-Listenern ohne Browserwarnung geliefert werden.

Die expliziten Caddy-Adressen `https://epiber.at:8081` und
`https://epiber.at:8082` garantieren auf diesen Ports keinen Redirect fuer
Plain-HTTP-Anfragen. Die Abnahme muss negativ pruefen, dass
`http://epiber.at:8081` und `http://epiber.at:8082` keine Anwendung und keine
API-Antwort ueber Klartext ausliefern. Verbindungsabbruch, TLS-Fehler oder eine
andere Ablehnung sind dort zulaessig; ein HTTP-Redirect ist kein Erfolgskriterium.

3. LAUFZEIT UND DEPENDENCIES
================================================================================

Erforderlich sind Node.js 26.x und npm 12.0.1. Andere Node-Major-Versionen sind
durch `engines` nicht freigegeben. Vor jeder Installation pruefen:

  node --version
  npm --version

Im jeweiligen Backend-Verzeichnis reproduzierbar installieren und pruefen:

  npm ci --omit=dev
  npm run build
  npm audit --omit=dev

`npm ci` muss das versionierte `package-lock.json` unveraendert verwenden. Der
Build fuehrt den statischen Check und die Tests aus. `package.json`,
`package-lock.json` und die spaetere `/version`-Antwort muessen exakt
`<FREIGEGEBENE_VERSION>` melden und zum freigegebenen Commit gehoeren. Ein
Branchsuffix oder eine geaenderte Lockdatei stoppt den Rollout.

4. SYSTEMBENUTZER, VERZEICHNISSE UND RECHTE
================================================================================

Einmalig als root:

  useradd -r -U -s /bin/nologin piber
  useradd -r -U -s /bin/nologin paj
  useradd -r -U -s /bin/nologin pk
  install -d -o root -g root -m 0755 /srv/http/ePiber
  install -d -o root -g root -m 0755 /srv/http/ePiber/piber
  install -d -o root -g root -m 0755 /srv/http/ePiber/paj
  install -d -o root -g root -m 0755 /srv/http/ePiber/pk

Alle Installations- und `systemctl`-Befehle dieses Dokuments werden als root oder
durch einen ausdruecklich autorisierten Betreiber ueber eng begrenztes sudo oder
polkit ausgefuehrt. Die Service-User `piber`, `paj` und `pk` besitzen eine
`nologin`-Shell, starten weder interaktive Sitzungen noch Deployments und duerfen
Caddy oder systemd-Dienste nicht selbst steuern. systemd wechselt nur fuer den
Node-Prozess auf den jeweiligen unprivilegierten Service-User.

Deployments erfolgen kontrolliert; Service-User benoetigen Leserechte auf Code
und `.env`, aber keine Schreibrechte im Checkout. Caddy benoetigt Leserechte auf
Frontend-Dateien und Suchrecht auf den Elternverzeichnissen. Schreibbarer
Laufzeitstate liegt ausschliesslich im jeweiligen systemd-StateDirectory.

Empfohlene lokale Rechte pro Instanz:

  Checkout/Code:                 root:root, Verzeichnisse 0755, Dateien 0644
  Backend/.env:                  root:<service-user>, 0640
  Credential-Quelldatei:         root:root, 0600
  /var/lib/epiber-<system>/:      <service-user>:<service-user>, 0700
  state.sqlite:                  <service-user>:<service-user>, 0600
  scorelog.sqlite:               <service-user>:<service-user>, 0600
  audit.sqlite:                  <service-user>:<service-user>, 0600

`StateDirectory=epiber-<system>` legt `/var/lib/epiber-<system>` mit dem in der
Unit gesetzten Modus 0700 an. Node erstellt `state.sqlite`, `scorelog.sqlite` und
`audit.sqlite` getrennt mit WAL, Foreign Keys, `synchronous=FULL` und Modus 0600.
Der State enthaelt Sessions, gehashte Tokens,
Resetnachweise, Monitorgeraete, idempotente Operationen, Loginlimits, Court-/
Navigator-State und Metadata-Intents. ScoreLog und Auditlog enthalten die
unbegrenzt aufbewahrte Fachhistorie. Jede SQLite-Datei mit ihrem `-wal` und
`-shm` nur bei gestopptem Dienst gemeinsam sichern oder je Datenbank ein
SQLite-Onlinebackup erstellen.

Historische Zeilen der bisherigen Google-Sheets-Tabs `ScoreLog` und `Logging`
werden nicht automatisch in diese Datenbanken importiert. Vor einer optionalen
Entfernung der Tabs sind ihre Inhalte separat gesichert zu archivieren.

6. CADDY INSTALLIEREN UND VALIDIEREN
================================================================================

Die aktuelle Vorlage verwendet fuer jede Origin:

  - CSP, nosniff, SAMEORIGIN, Referrer- und Permissions-Policy sowie COOP.
  - `connect-src` nur fuer die jeweilige HTTPS/WSS-Origin.
  - Proxy nur fuer `/ws`, `/api/*`, `/live`, `/ready`, `/health`, `/version`,
    `/status` auf den jeweiligen Loopback-Port.
  - Statische Auslieferung aus dem systemspezifischen `Frontend/` mit no-cache.

Als root installieren, vor Reload validieren und Zertifikate kontrollieren:

  install -o root -g root -m 0644 Project/server-configs/Caddyfile /etc/caddy/Caddyfile
  caddy validate --config /etc/caddy/Caddyfile
  systemctl enable --now caddy
  systemctl reload caddy
  systemctl status caddy
  journalctl -u caddy --since today

Unbekannte Backendpfade duerfen nicht am Node-Prozess ankommen. Statische Pfade
duerfen keine `.env`, Credentials, SQLite-Dateien oder Backendquellen ausliefern,
weil jeder Caddy-Root exakt auf das jeweilige `Frontend/` zeigt.

7. SYSTEMD INSTALLIEREN UND VALIDIEREN
================================================================================

Die drei Vorlagen setzen je System:

  User/WorkingDirectory/EnvironmentFile  systemspezifisch
  INSTANCE_ID                            piber, paj oder pk
  LISTEN_HOST                            127.0.0.1
  PUBLIC_ORIGIN                          jeweilige HTTPS-Origin
  STATE_FILE                             /var/lib/epiber-<system>/state.sqlite
  SCORELOG_FILE                          /var/lib/epiber-<system>/scorelog.sqlite
  AUDITLOG_FILE                          /var/lib/epiber-<system>/audit.sqlite
  GOOGLE_APPLICATION_CREDENTIALS         %d/google-service-account
  LoadCredential                         root-kontrollierte Quelldatei
  SHUTDOWN_GRACE_MS                      90000
  KillSignal/TimeoutStopSec              SIGTERM / 95 Sekunden
  StateDirectory/Mode                    epiber-<system> / 0700
  UMask                                  0077
  SyslogIdentifier                       epiber-<system>
  Journal-Rate-Limit                     1000 Events je 30 Sekunden

Sandbox: NoNewPrivileges, PrivateTmp, PrivateDevices, ProtectSystem=strict,
ProtectHome sowie Kernel-, ControlGroup- und Clock-Schutz; keine Capabilities,
keine SUID/SGID-, Realtime-, Namespace- oder fremde Architekturfreigabe; nur
AF_UNIX, AF_INET und AF_INET6.

Vorlagen aus dem freigegebenen Commit mit Paketversion
`<FREIGEGEBENE_VERSION>` installieren:

  install -o root -g root -m 0644 Project/server-configs/systemd/*.service /etc/systemd/system/
  systemd-analyze verify /etc/systemd/system/epiber-piber.service
  systemd-analyze verify /etc/systemd/system/epiber-paj.service
  systemd-analyze verify /etc/systemd/system/epiber-pk.service
  systemctl daemon-reload
  systemctl enable epiber-piber epiber-paj epiber-pk

Die journald-Vorlage als root installieren und journald neu starten:

  install -d -o root -g root -m 0755 /etc/systemd/journald.conf.d
  install -o root -g root -m 0644 Project/server-configs/journald/epiber.conf /etc/systemd/journald.conf.d/epiber.conf
  systemctl restart systemd-journald

Die Vorlage speichert persistent, begrenzt alle Systemjournale gemeinsam auf 1 GiB
und behaelt Eintraege maximal 14 Tage. Diese Werte sind vor Installation gegen
Platzangebot und betriebliche Aufbewahrungsanforderungen zu pruefen. journald ist
trotz Persistenz nur Diagnosekanal; Score-/Audit-Historie bleibt in SQLite.

Nicht alle Systeme bei einer Versionspromotion gleichzeitig starten. Die
Reihenfolge PAJ, PK, Live einhalten. Beim Stop sendet systemd SIGTERM. Der Server
nimmt keine neue Arbeit an, setzt Liveness auf stopping, stoppt Poller, schliesst
WebSockets mit 1012, drainiert HTTP-/Sheets-Arbeit und schliesst alle drei
SQLite-Datenbanken. Nach 95
Sekunden greift systemd ein; ein Timeout oder Exitcode ungleich null ist ein
fehlgeschlagener Rollout und kein erfolgreicher Stop.
Die Bewertung aller dabei beobachteten Codes, insbesondere 1012, erfolgt nach
`Project/software/WEBSOCKET-CLOSE-CODES.txt`.

8. START, HEALTH UND STATUS
================================================================================

Jeweils nach Migration, Installation und Build starten, zunaechst nur PAJ:

  systemctl restart epiber-paj
  systemctl status epiber-paj
  journalctl -u epiber-paj --since "10 minutes ago"

Kurzes Journal-Follow-Runbook fuer root oder autorisierte Betreiber:

  1. In einem separaten Terminal `journalctl -u epiber-paj -f --since now`
     starten; fuer PK oder Live den Unitnamen entsprechend ersetzen.
  2. Im Arbeitsterminal den Dienst neu starten und die vorgesehenen Health- und
     Funktionstests ausfuehren.
  3. Im Follow-Terminal Startmeldung, Initialisierung, Testzeitpunkt und neue
     Warnungen/Fehler beobachten; bei einem Fehler den Zeitpunkt und die
     betroffene Unit festhalten.
  4. Follow mit Ctrl-C beenden und den relevanten Zeitraum bei Bedarf mit
     `journalctl -u <unit> --since "<ZEITPUNKT>" --no-pager` erneut ausgeben.
     Personenbezogene Werte und Geheimnisse nicht ungefiltert in Tickets oder
     Freigabeprotokolle uebernehmen.

Oeffentliche Checks pro Origin:

  curl --fail --show-error https://epiber.at:8081/version
  curl --fail --show-error https://epiber.at:8081/live
  curl --fail --show-error https://epiber.at:8081/ready
  curl --fail --show-error https://epiber.at:8081/health

Fuer PK Port 8082, fuer Live keinen Port angeben. Erwartung:

  /version    HTTP 200 und exakt {"version":"<FREIGEGEBENE_VERSION>"}
  /live       HTTP 200, status ok, Version <FREIGEGEBENE_VERSION>
  /ready      HTTP 200, status ready, Version <FREIGEGEBENE_VERSION>
  /health     wie /ready; waehrend Initialisierung/Fehler HTTP 503

`/status` ist absichtlich admin-geschuetzt. Es ist im Browser mit einer echten
Admin-Session oder mit einem kontrolliert bereitgestellten Sessioncookie zu
pruefen; ein anonymer Curl muss 401 liefern. Der Detailstatus muss Readiness,
Poller, Tabellenalter/-fehler, Courtquelle, WebSocketprovider, Monitore,
Court-State, aktive Sheets-Writes/Queues und `pendingMetadataIntents` plausibel
zeigen. `scoreLog` und `auditLog` muessen offen/ready sein und plausible
Schreibzaehler liefern; Ereigniszeilen werden ueber `/status` nicht ausgegeben.
Die Antwort darf keine Secrets enthalten. Unbekannte Fachwrite-Ausgaenge werden
akteursbezogen ueber den RPC `operationStatus` abgefragt.

Die `/status`-Antwort ist trotz fehlender Secrets eine geschuetzte Sammlung
personenbezogener Betriebsdiagnosen. Sie kann insbesondere IP-Adressen,
Benutzer-IDs und -namen sowie stabile Client-/Geraetekennungen verbundener
Sockets enthalten. Zugriff und Auswertung sind auf Administratoren und
autorisierte Betreiber fuer den konkreten Betriebszweck zu begrenzen. Antwort,
Screenshots und Auszuege duerfen nicht auf oeffentlichen Anzeigen erscheinen und
nicht ungefiltert in Journale, Tickets oder Freigabeprotokolle kopiert werden;
die HTTP-Antwort bleibt `no-store`.

`audit.sqlite` enthaelt zusaetzlich geschuetzte personenbezogene Historie:
Namenssnapshots sowie bei Loginversuchen vollstaendige normalisierte gueltige
E-Mail-Adressen und Quell-IPs. Diese Werte werden derzeit nicht automatisch
geloescht und muessen in Zugriffsschutz, Sicherung und einer spaeteren
kontrollierten Loeschung oder Anonymisierung einschliesslich Backups
beruecksichtigt werden. Der journald-Spiegel enthaelt E-Mail und IP nur maskiert.

Bei der Courtsteuerung friert das Deaktivieren eines Platzes den zuletzt
akzeptierten Score ein. Ein expliziter Reset setzt nur diesen Platz sofort auf
Null. Aktivierung und Reset setzen eine neue Court-Epoch und warten auf eine
gegenueber der ersten externen Baseline geaenderte Quelle; dadurch koennen weder
die unveraenderte externe Vorreset-Anzeige noch ein vor dem Zustandswechsel
gestarteter Poll den Nullstand ueberschreiben. Nur danach akzeptierte semantische
Scoreaenderungen werden vor Anzeige und Push synchron in `scorelog.sqlite`
geschrieben; Reset und Baseline selbst erzeugen keinen ScoreLog-Eintrag. Bei
Insertfehler bleibt der bisherige sichtbare Score erhalten und der Folgepoll
versucht die Aenderung erneut. Bei Prozessstart
uebernimmt ein in SQLite bereits aktiver Platz den ersten externen Stand sofort in
die Anzeige, ohne diesen Wiederanlaufstand zu protokollieren.

Zusaetzliche Betriebschecks:

  ss -ltnp
  systemctl status caddy epiber-paj epiber-pk epiber-piber
  journalctl -u epiber-paj -f

Die Node-Ports duerfen nur auf 127.0.0.1 lauschen. Browser-DevTools muessen fuer
alle Systeme HTTPS-Dokumente, einen WSS-Upgrade auf same-origin `/ws`, Welcome v2
und keine Mixed-Content-, CSP-, Zertifikats- oder Originfehler zeigen.


================================================================================
9. ROLLOUT UND ROLLBACK
================================================================================

Die vollstaendige fachliche und technische Abnahme steht in
ROLLOUT-CHECKLIST.md. Kurzregel:

  1. Sheets sowie alle drei SQLite-Datenbanken sichern, Schema/Credentials pruefen.
  2. Exakten Release-Commit und Lockfile auf PAJ installieren und abnehmen.
  3. Exakt denselben Commit auf PK installieren und Smoke-/Integrationscheck.
  4. Exakt denselben Commit zuletzt auf Live installieren und eng beobachten.

Vor jeder Stufe den vorherigen Commit/Release, `.env`, Credential-Zuordnung,
Caddy-/systemd-Version und konsistente Backups festhalten. Rollback bedeutet
Code und Vorlagen auf den dokumentierten vorherigen Stand zurueckzusetzen und,
nur wenn das neue Schema oder der neue State nicht abwaertskompatibel ist, die
zugehoerigen konsistenten Sheets-/SQLite-Backups wiederherzustellen. Niemals nur
eine einzelne SQLite-WAL-Datei oder ein einzelnes Sheet-Tab zurueckspielen.
